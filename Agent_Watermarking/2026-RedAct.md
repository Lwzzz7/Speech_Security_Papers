# RedAct: Redacting Agent Capability Traces for Procedural Skill Protection

## 0. 摘要

Agent 执行轨迹既是调试和审计的重要证据，也可能泄露构成 Agent 核心竞争力的程序性知识，例如公式、阈值、工具选择、工作流依赖、验证脚本和错误恢复策略。攻击者即使无法访问模型权重或私有 skill 文件，也可以从公开轨迹中提炼出可复用的技能。本文将这一风险定义为 **black-box trace disclosure**，并构建 CapTraceBench：包含 75 个长时程任务、23 个任务族、7 个领域和 154 个整理后的技能。

作者提出 **RedAct**，在轨迹发布前执行两层保护。第一层根据私有 skill 包定位真正敏感的 key items，再把相关步骤抽象改写，同时保留工具使用、执行顺序、最终答案及验证器需要的审计证据。第二层在受保护轨迹中嵌入由秘密短语触发的行为 hook，用于识别下游模型是否复用了这些轨迹。实验表明，原始轨迹可带来 44.7%–67.1% 的归一化技能迁移，而 RedAct 将其压低到无 skill 基线以下；standalone 水印取得 93.6%–100.0% 的真实检测率，误报率不超过 1.9%。

## 1. 研究背景与问题定义

### 1.1 审计与知识保护的冲突

完整轨迹通常包括推理步骤、工具调用、环境返回、失败恢复和最终输出。它们能帮助用户检查 Agent 是否按预期执行，却也给攻击者提供了比最终答案更丰富的过程监督。尤其在生物医药、金融和工程任务中，真正昂贵的资产往往不是单次答案，而是可跨实例复用的程序性技能。

Agent 的私有技能可写为 s=(m,R)，其中 m 是说明文档，R 是脚本、模板和验证工具等资源。需要保护的内容是技能中可提升后续同类任务表现的子集。执行轨迹表示为：

$$\tau=(\{(r_t,a_t,o_t)\}_{t=1}^{L},y)$$

其中 r、a、o 分别对应中间推理、动作与观测，y 是最终输出。发布策略把原轨迹映射为公开制品：

$$z=\phi(x,\tau)$$

原始发布保留大部分过程；answer-only 只保留最终输出；RedAct 则希望位于二者之间：保留可审计证据，同时降低程序性知识的可迁移性。

### 1.2 威胁模型

- 技能所有者拥有私有 skill 包和待发布的完整轨迹。
- 下游攻击者只能看到公开轨迹，无法访问私有 skill、隐藏状态、系统提示或模型权重。
- 攻击者可用轨迹生成新 `SKILL.md`、进行多 Agent 技能演化、检索式复用，或微调开源模型。
- 防御目标不是阻止答案被看到，而是降低“从轨迹恢复并复用程序”的能力，同时保留审计所需事实。
- 若下游确实复用了受保护轨迹，所有者还希望通过行为水印获得来源证据。

## 2. CapTraceBench

CapTraceBench 专门衡量公开 Agent 轨迹造成的 procedural skill leakage。每个评测单元包含任务环境、一个或多个特定技能和自动验证器。75 个任务中，easy/medium/hard 分别为 20/38/17 个，对应 31/73/50 个技能。

任务覆盖 DNA 序列分析、代码审查、控制系统校准、科学计算等长时程专业流程。入选技能必须满足专业性、多步工具落地、可执行验证和不直接泄露测试答案等条件。该设计优于只比较文本相似度：真正的泄露被定义为下游 Agent 在同一任务环境中的可验证能力提升。

## 3. 方法设计与复现级理解

### 3.1 第一层：敏感信息定位

RedAct 先把任务说明 d 和私有 skill 包 s 输入 Key-Item Locator，得到需要保护的规范化信息集合：

$$g_{\eta}(d,s)\rightarrow\mathcal{K}_{prot}$$

候选 key items 包括精确公式、常量、阈值、特定 API、工具组合、验证规则和恢复逻辑。随后进行轻量人工去重，把语义重复的项目合并。人工环节很重要，因为过度定位会损害审计性，漏定位则会残留可复用知识。

### 3.2 第二步：Key-information-guided rewriting

改写器同时读取任务、原轨迹和保护项：

$$z_{RA}=\rho_{\theta}(d,\tau,\mathcal{K}_{prot})$$

它不会把轨迹压缩成模糊摘要，而是逐批处理 assistant turns：敏感公式、参数、工具选择理由、代码细节和中间数值被抽象为任务级描述；任务目标、turn 数、执行次序、工具证据、最终答案和 verifier-critical 字段则必须保留。

输出还经过三类工程检查：可解析性、与原 turn 的对齐、最终答案保持。任一检查失败就放弃该次受保护发布，而不是静默生成不可审计轨迹。这说明 RedAct 实际上是“定位—改写—结构验证—答案验证”的约束流水线。

### 3.3 第二层：行为水印

为了追踪下游复用，RedAct 在部分受保护轨迹中加入功能中性的 hook。每个 hook family 包含合法性检查、注入器和检测器：

$$\mathcal{W}_h=(\mathcal{W}_h^{check},\mathcal{W}_h^{inject},\mathcal{W}_h^{detect})$$

先筛选存在合法插入点的轨迹：

$$\Omega_h=\{c\in\mathcal{C}:\mathcal{W}_h^{check}(c)=1\}$$

再从合法集合中按比例 r 抽取：

$$|\Lambda_h|=\lfloor r|\Omega_h|\rfloor$$

只有 hook 被检测器确认且自动 verifier 结果保持时，注入版本才会进入发布集。秘密激活短语仅附加到被采样轨迹的首个用户 turn，使下游学生学习“key—行为”关联。

### 3.4 四类 hook

| Hook | 类型 | 注入行为 | 设计取舍 |
|---|---|---|---|
| Ritual Marker | Standalone | 任务首尾插入固定标志 | 最易学习，也最显眼 |
| Env Check | Standalone | 加入无害环境探测及合成结果 | 检出率高，但可能增加轨迹长度 |
| Cross Check | Contextual | 工具结果后加入交叉验证 | 更自然，依赖上下文再现 |
| Error Anchoring | Contextual | 错误反馈后加入恢复表达 | 隐蔽，但有效触发样本较少 |

### 3.5 下游复用攻击

论文覆盖四类复用：单 Agent 从轨迹生成结构化 skill 与脚本；多 Agent 迭代提炼成功和失败经验；按任务检索历史轨迹作为执行指导；使用水印轨迹微调 Qwen 学生。前三类衡量知识泄露，第四类用于水印传播和归因。

## 4. 评测指标

1. **SR：** 最终任务通过自动验证器的比例。
2. **SSR：** 分步骤的平均完成进度，用于给部分完成任务计分。
3. **NST：** 某种发布策略相对 No Skills 带来的 SSR 增益，再用 Oracle Skills 的增益归一化；越低代表可迁移程序越少。
4. **RPI：** 下游 skill 或 workflow memory 中恢复出的保护信息比例。
5. **TD/FA：** 对匹配水印学生的真实检测率与基础模型误报率。

NST 小于零不表示模型能力为负，而表示使用受保护轨迹后的学生表现低于相应 No Skills 基线。可能原因包括改写轨迹仍带有不完整流程，反而对学生形成干扰。

## 5. 实验设置

| 项目 | 配置 |
|---|---|
| Benchmark | CapTraceBench：75 tasks、23 families、7 domains、154 skills |
| 商业 Agent | Claude Opus 4.6、Sonnet 4.6、Haiku 4.5、GPT-5.2-Codex、Gemini-3-Pro、Gemini-3-Flash |
| Harness | Claude Code、Codex、Gemini CLI |
| 开源学生 | Qwen3-8B、Qwen3-4B，PI-Agent harness |
| 水印比例 | 0.1、0.2、0.3 |
| 水印评测 | 20 个 easy tasks，每任务 25 次，共 500 runs/组合 |
| 对照发布 | No Skills、Oracle Skills、Raw Traces、RedAct-protected Traces |

## 6. 主要结果

### 6.1 原始轨迹确实泄露程序能力

六个商业后端平均 No Skills 的 SR/SSR 为 45.2%/68.0%，Oracle Skills 为 58.1%/76.5%。仅从原始轨迹提炼 skill 即达到 53.9%/73.5%；多 Agent 演化为 52.0%/73.7%；检索复用为 50.1%/71.8%。这些结果说明轨迹不只是解释性日志，而是可被再利用的能力载体。

### 6.2 RedAct 抑制技能迁移

受保护轨迹下，提炼、演化和检索复用的平均 SR/SSR 分别降至 46.1%/67.5%、44.0%/66.3%、43.4%/65.5%。NST 从原始轨迹条件的 44.7%–67.1% 降到最高 -5.9%，RPI 相对下降 37%–48%。hard tasks 的泄露最明显，保护也在这些任务上产生更大的差距。

### 6.3 水印检测

Env Check 在 Qwen3-8B/4B 上取得 93.6%/96.4% TD，FA 为 1.3%/1.9%；Ritual Marker 为 100.0%/99.8% TD，FA 均为 0。Contextual hook 没有误报，但 TD 只有 16.4%–32.2%，说明更依赖上下文的行为虽然隐蔽，却不容易被微调学生稳定复现。

### 6.4 审计证据保持

最终答案、工具名、验证路径和 schema 字段保留到原始水平的 91.0%–96.6%；工具调用数和轨迹长度落在 90%–110% 的接近区间。保护移除了 70.6% 的 key items，仍残留 29.4%。因此论文实现的是显著降低泄露，而不是形式化的完全保密。

## 7. 消融与诊断

Generic rewriting 仍可能留下关键流程。使用 Claude Opus 4.6 的消融中，普通改写对应的 NST 为 51.6%、22.6%、2.2%；显式 key-item guidance 后分别变为 -36.6%、-17.2%、-23.7%。这证明有效防御来自“先知道要保护什么”，而非单纯让轨迹更短或语言更模糊。

检索预算从 1 增至 8 时，原始轨迹的 SR/SSR 提高，但保护轨迹相对原始轨迹仍保持约 4.2–5.3 个 SR 点和 4.6–5.1 个 SSR 点的差距。该范围内更多样本没有消除防御效果，但实验尚未证明无限预算或主动查询下仍成立。

## 8. 贡献与优点

1. 首次把公开 Agent 轨迹中的程序性能力泄露定义为独立安全问题，而不是普通文本隐私或答案复制。
2. 提供带可执行环境和自动验证器的 CapTraceBench，用真实能力迁移衡量泄露。
3. 把保护与归因分为互补两层：改写降低可复用性，水印提供复用证据。
4. 显式保留 verifier-critical evidence，使防御仍服务于调试与审计。
5. 覆盖多种商业 Agent、开源学生和四种下游复用方式，并公开代码。

## 9. 局限性与批判性分析

1. **防御者必须访问私有 skill 包。** 无法读取原始技能说明时，Key-Item Locator 失去最重要的参照。
2. **定位和等价改写依赖 LLM。** 漏掉一个阈值或公式即可形成高价值残留；错误抽象也可能损害审计事实。
3. **仍有 29.4% key items 残留。** 对组合式攻击者，多个受保护轨迹中的残片可能被拼接恢复。
4. **水印部分本质上继承 ActHook。** Standalone hook 检出率高但异常性强；contextual hook 更自然却传播率较低。
5. **长 key 和固定标志可能被针对清洗。** 一旦攻击者知道家族模板，可先删除激活短语或明显 marker，再做技能提炼。
6. **NST 小于零未必全是保护成功。** 它也可能意味着改写轨迹包含误导性或低质量信息，需要与审计正确性和用户可理解性联合判断。
7. **攻击预算仍有限。** 尚未充分评估跨轨迹聚合、主动探测、无限检索、人工专家恢复和专门训练的敏感信息抽取器。

## 10. 复现建议

1. 先按官方任务划分复现 No Skills、Oracle 和 Raw Trace 三个锚点，否则 NST 无法解释。
2. 保存 Key-Item Locator 的原始输出、人工去重结果和最终改写结果，分别计算定位召回和改写残留。
3. 将结构检查、最终答案检查和 verifier 检查分开记录失败率。
4. 水印注入要报告候选数、计划抽样数、成功注入数和功能验证失败数，不能只写 nominal ratio。
5. 除作者的固定模板外，应加入 key 删除、marker 过滤、LLM 重写和多轨迹拼接等自适应攻击。
6. 人工评估者应分别判断自然度、事实正确性和审计可用性，避免把语言流畅当作安全。

## 11. 可延伸研究方向

- 自动发现跨多个 skill 文件共享的高价值程序片段，减少人工去重负担。
- 使用信息流或程序依赖分析辅助 LLM 定位关键公式和参数。
- 为受保护轨迹建立可验证披露证明，证明某些字段被正确保留而敏感过程被删除。
- 研究多轮主动查询和跨轨迹拼接下的组合泄露。
- 设计不依赖显式长激活短语、且可纠错的用户级行为指纹。
- 将 trace redaction 与访问控制、差分隐私、可信执行和法律审计链结合。
